**第三步，按 `docs/handoff/R1_DATA_MODEL.md` 实施。**

核心目标一句话：**同一部电影无论看几次、写几条感想，在数据里只有一个 Work。**

需要特别注意：

- 本窗口**不做任何 UI 改动**。UI 在 R2–R4
- 迁移**必须先导出 JSON 备份**，**必须幂等**，**必须可回滚**。备份失败则终止迁移
- 票价的红线本次变更：**不再脱敏，正常记录并可导出**。但姓名、邮箱、手机号、订单号、取票码、二维码令牌、支付方式与卡号**仍然强制移除**。`tests/ticket.test.mjs` 里断言「票价被移除」的用例需要反转
- 票价**不得**进入 AI 请求体
- 初看／重看由系统按时间顺序推定，**AI 不得参与**
- **「初看／重看」与「在哪看的」完全正交，代码里不得有任何「影院＝初看」的假设。** 用户可能先在家看过、之后趁重映才去影院，此时影院那次是重看。`assignViewingRelations` 的实现里不应该读到 `location_type` 这个字段。`watch_index` 无上限，第 7 次就是 7
- **每次写入或修改 ViewingEvent 后，都要对该作品的全部事件重跑一遍推定并整体回写**。用户补录一次更早的观看时，原来的「初看」要正确变成「重看」
- **「制式」与「活动」是两类东西，必须分流**：IMAX / Dolby / 4DX 是影厅硬件规格，进 `format`（单值）；舞台挨拶 / 応援上映 / 先行上映 / 入場者特典 是这一场的性质，进 `event_types`（数组）。现有 `extractFormatAndTitle` 把片名里的 `【...】` 一律当制式，所以 `【舞台挨拶付き】` 现在被错误地存成了制式。这是本项目的高频场景，务必做对
- `work_type` 与 `event_types` **不得互相推导**
- **顺手把 `Work.release_dates` 采下来**（Bangumi 条目的 `date` → `release_dates.jp`）。这是 W14 纪念日功能的数据基础；R1 正在迁移，现在加几乎零成本，等以后再加就要对全部存量 Work 再迁一次
- 不使用私人真实感想原文做测试夹具

**交付：**冲突清单 → 代码 → 全量测试结果 → 迁移在真实存量数据上的执行报告 → `docs/IMPLEMENTATION_STATUS_R1.md` → 给 R2 的接口说明。
