日期：2026-08-03
角色：本文件由产品经理／系统架构师窗口产出，供 R1–R5 执行窗口（Sonnet）实施
状态：已获用户四项关键决策确认，可执行
优先级：**本方案必须在 W6（情绪标签）之前完成**

---

## 0. 这次调整为什么必须先做

W6–W9 要做的是「记忆卡片」的完整能力：情绪标签、44 种类型库、卡片编辑与排序、初看／重看关系。

这些卡片都要挂在某个对象上。但当前代码里，卡片挂在 `record` 上，而 `record` 同时又是「作品」的唯一载体——**同一部电影看两次，会产生两个互不相识的作品条目**。

如果先做 W6–W9，46 个情绪标签和 44 种卡片类型会全部长在一个错误的对象关系上，之后再改数据模型，卡片、标签、排序都要跟着返工。

**用户的判断是对的：结构调整必须前置。** 本方案把它拆成 R1–R5 五个执行窗口。

## 2. 三条必须先解决的架构债

### 债 1：Work 不是一个真正的实体（阻塞级）

**代码证据：**

```js
// src/app.js  finishCompose()
record.workId = `work_${record.id}`;
const work = createLocalWork(record);
await db.putRecordWithWork(record, work);
```

```js
// src/domain.js  createLocalWork()
const workId = record.workId || `work_${record.id}`;
```

Work 的 ID 由 Record 的 ID 派生，因此 **Work 与 Record 是一对一的**。

**后果链：**

- 同一部电影看 N 次 → N 个作品条目，互不关联
- 「按作品聚合感想」（用户第 3 点）在数据层不可能实现
- 「初看／重看」无法判定——系统不知道这部电影之前看过
- 每次记录都要重新向 Bangumi 匹配一遍同一部作品
- 首页壁纸候选池里同一部电影重复出现
- 未来年度报告的「今年看了多少部电影」会严重偏高

### 债 2：Record 同时承担三种语义

当前一条 `record` 同时是：①一次观影事件、②一份感想文本、③一个作品的载体。

三者的生命周期完全不同：作品资料是长期稳定的；观影事件是一次性的、有时间地点的；感想可以在观影后立刻写、也可以多年后补写。挤在一个对象里，任何一种关系变化都会污染另外两种。

### 债 3：ViewingEvent 只在粘贴票务时才存在

`viewingEvents` store 只有走票务粘贴路径才会写入。线上／家中观看完全没有观影事件记录。

这直接导致用户第 2 点（首页展示「鉴赏履历」）无法统一实现——线上记录没有可展示的履历数据。

## 3. 目标数据模型（三层）

```
Work（作品资料 · 长期稳定 · 一部电影一条）
  │
  ├── ViewingEvent（观影事件 · 一次具体观看 · 有时间地点）
  │      └── Record（感想记录 · 这次看完写的东西）
  │
  ├── ViewingEvent（第二次观看 · 在家重看）
  │      └── Record
  │
  └── Record（补充记录 · 无新观影事件 · 多年后重评 / 看完续作回头补）
```

关系约束：

- `Work 1 —— N ViewingEvent`
- `ViewingEvent 1 —— 0..1 Record`（先有票、后补感想是允许的）
- `Record N —— 1 Work`（必填）
- `Record 1 —— 0..1 ViewingEvent`（可空 = 补充记录）

### 3.1 Work（作品资料）

| 字段 | 类型 | 说明 | 状态 |
|---|---|---|---|
| `id` | string | **改** `work_bgm_{subjectId}`（已匹配）／ `work_local_{slug}`（仅本地） | 改造 |
| `title` | string | 主标题 | 有 |
| `original_title` | string\|null | 原名 | 有 |
| `aliases` | string[] | 别名，用于查重 | 有 |
| `work_type` | enum | **新** `animation_film` / `live_action_film` / `event` / `other` / `unspecified`（理念 #3 明确要求） | 新增 |
| `release_year` | number\|null | 改为由 `release_dates.jp` 派生，无日期时仍可独立填写 | 有 |
| `release_dates` | object | **新** `{ jp: "YYYY-MM-DD"\|null, cn: "YYYY-MM-DD"\|null, other: [] }`，支撑纪念日（提案 M） | 新增 |
| `external_refs` | array | `[{source:"bangumi", id}]` | 有 |
| `identity_status` | enum | `local_only` / `matched` | 有 |
| `poster_subject_id` | string\|null | **新** 海报取图用，履历卡与书架依赖 | 新增 |
| `merged_from` | string[] | **新** 迁移时被合并掉的旧 work id，保证旧引用不失效 | 新增 |
| `first_recorded_at` | ISO | **新** 首次记录时间 | 新增 |
| `match` | object | 匹配状态机 | 有 |

**ID 策略与查重顺序（`resolveWork`）：**

1. 有 Bangumi subject ID → `work_bgm_{subjectId}`，命中即复用
2. 无 subject ID → 在现有 works 里按 `aliases` 精确匹配
3. 再按 `normalizeTitle(title)` 匹配（去空格、全半角统一、去 `【制式】` 前缀、繁简不做归一）
4. 都不命中 → 新建 `work_local_{slug}`
5. 某个 local work 之后匹配到 Bangumi → 升格为 `work_bgm_*`，旧 id 记入 `merged_from`

### 3.2 ViewingEvent（观影事件）

| 字段 | 类型 | 说明 | 状态 |
|---|---|---|---|
| `id` / `viewing_id` | string | | 有 |
| `work_id` | string | 指向 Work | 有 |
| `record_id` | string\|null | 指向 Record | 有 |
| `location_type` | enum | **扩展** `cinema` / `home` / `online` / `other`（原来只有 `cinema`） | 改造 |
| `viewed_on` / `screening_at` / `screening_ends_at` | ISO | | 有 |
| `duration_minutes` | number\|null | **新** 由 `screening_ends_at - screening_at` 派生，理念 #3 要求 | 新增 |
| `viewing_relation` | enum | **启用** `first` / `rewatch`；系统推定，用户可改 | 改造 |
| `watch_index` | number | **启用** 该 work 下的第几次观看，从 1 开始 | 改造 |
| `ticket_price` | object\|null | **新** `{amount:number, currency:"JPY"}`，见第 9 节红线变更 | 新增 |
| `viewing_context.cinema_name / city / format / seats / seat_count / ticket_provider` | | | 有 |
| `viewing_context.event_types` | string[] | **新** 影院活动多选，见提案 I；与 `format`（硬件制式）严格区分 | 新增 |
| `viewing_context.bonus_note` | string\|null | **新** 入场者特典的自由文本备注 | 新增 |
| `screened_content` | object | 全片／集数范围 | 有 |
| `source` | enum | **新** `ticket_paste` / `manual` / `none` | 新增 |
| `status` / `confirmed_at` | | | 有 |

**`viewing_relation` 推定规则（R1 实现）：**
查该 `work_id` 下已有的 ViewingEvent，按 `screening_at` 排序，本次时间最早 → `first`，否则 → `rewatch`；`watch_index` = 排序后的序号。系统推定后写入，用户可在确认卡与详情页一键翻转。**AI 不参与推定。**

#### ⚠️ 初看／重看与观看地点完全正交

**`viewing_relation` 只由时间顺序决定，与 `location_type` 没有任何关系。** 代码里不得出现任何形式的「影院＝初看」假设。真实存在的组合至少有：

| 情况 | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| 影院初看，回家重看 | 影院 · first | 在家 · rewatch | |
| **在家初看，之后趁重映去影院** | **在家 · first** | **影院 · rewatch** | |
| 影院看完意犹未尽，同期二刷影院 | 影院 · first | 影院 · rewatch | |
| 反复重看 | 在家 · first | 在家 · rewatch | 在家 · rewatch … |

`watch_index` **无上限**，第 7 次就是 7。UI 不得假设只有两三次。

#### ⚠️ 补录早期观看会导致序号重排

用户可能今天记录了影院观影，之后才想起来「其实几年前在家看过」并补录一次更早的观影事件。此时：

- 新事件时间更早 → 它变成 `first`，原来的 `first` 变成 `rewatch`
- 该 work 下**全部** ViewingEvent 的 `watch_index` 必须整体重算，不能只给新事件递增编号
- 因此每次写入或修改 ViewingEvent 后，都要对该 work 的全部事件重跑 `assignViewingRelations`
- 若某个事件被用户手动锁定（`relation_locked: true`）而重排后与时间顺序矛盾 → **保留用户的选择，但在该事件上标 `relation_conflict: true`**，由 R4 作品页显示一行温和提示，让用户自己决定。系统不得擅自覆盖用户的判断，也不得假装没有矛盾。

### 3.4 迁移（用户已确认：自动迁移合并）

一次性迁移脚本，D1 与 IndexedDB 双路径都要生效：

1. **迁移前自动导出一份完整 JSON 备份**到本地（复用 `src/export.js`），文件名带时间戳
2. 扫描全部 works，按 §3.1 查重顺序分组
3. 每组选主：优先已匹配 Bangumi 的、其次 `createdAt` 最早的
4. 被合并的 work → 其 id 写入主 work 的 `merged_from`，`aliases` 并集去重
5. 全部 records 的 `workId` → 重写为 `work_id` 指向主 work，补 `record_kind: "viewing"`
6. 无 ViewingEvent 的旧 record → 补建一个 `location_type: "online"`、`source: "none"` 的 ViewingEvent（因为无从判断，标 `needs_review: true`，在详情页显示「这条记录的观看场景待确认」）
7. 按 §3.2 规则回填全部 `viewing_relation` 与 `watch_index`
8. 迁移带版本标记 `meta.migration_version = "r1-work-dedup"`，**幂等**，重复执行不产生副作用
9. 迁移失败 → 完全回滚，保留原数据，提示用户

## 4. 新用户流程（用户第 1 点 + 我的补充）

### 4.1 当前流程（问题）

```
点「＋」→ 立刻弹出 textarea + 键盘 → 用户自己打 #作品名 #电影院 → 完成
                                    ↑ 票务按钮藏在工具栏，多数人不会点
```

用户被迫用「打 # 标签」这种通用笔记手法，去表达「我在影院看了某部电影」这件本该由 App 自动知道的事。

### 4.2 新流程

```
点「＋」
  │
  ├─[Step 1 · 场景识别]────────────────────────────────
  │   大面积粘贴区："粘贴票务信息，或跳过"
  │   ┌ 剪贴板已有票务文本 → 顶部横幅「检测到票务信息 · 一键使用」（提案 A）
  │   └ 两个次要入口：「没有票，直接写」
  │
  ├─[粘贴分支]
  │   本地脱敏 → 解析 → 作品匹配（Bangumi）
  │   ↓
  │   [Step 2 · 确认卡] 一屏、一个「确认」按钮：
  │     海报 + 作品名（可换候选 / 手动改）
  │     影院 · 日期时间 · 制式 · 座位 · 时长 · 票价
  │     初看／重看（系统已推定，一键翻转）
  │
  ├─[跳过分支]（用户已确认：给两个按钮）
  │   [Step 2' · 场景二选一]
  │     ①「在家 / 线上」→ location_type: home
  │     ②「在影院（手填）」→ 展开影院名 + 制式两个输入框 → location_type: cinema
  │   两者都可再选初看／重看
  │
  └─[Step 3 · 随手写]
      作品与场景已在后台确定，用户**不需要再打任何 #**
      顶部一行灰色小字提示当前上下文：「《作品名》· 2026/08/03 · TOHO 新宿 · IMAX」
      → 完成 → AI 后台整理 → 自动保存备份
```

**关键收益：** `#` 从「必须的语法」降级为「可选的强调手法」。这才是「面向电影的专用记录流程」（理念 #2）。

### 4.3 补充记录从哪里发起（提案 E）

「＋」永远意味着**「我刚看完」**。多年后重评、看完续作回头补——这类补充记录从**作品页**发起（R4 交付），生成 `record_kind: "supplement"`、`viewing_event_id: null` 的记录。

这样一来，理念 #4 的四种场景全部有明确入口：

| 场景 | 入口 | 数据表现 |
|---|---|---|
| 影院观看 | ＋ → 粘贴票务 | ViewingEvent(cinema) + Record(viewing) |
| 在家 / 线上观看 | ＋ → 跳过 → 在家 | ViewingEvent(home) + Record(viewing) |
| 影院观看但无票务邮件 | ＋ → 跳过 → 在影院（手填） | ViewingEvent(cinema, source: manual) + Record(viewing) |
| 多年后重新评价 | 作品页 → 补充记录 | Record(supplement)，无新 Event |
| 看续作后回头补充 | 作品页 → 补充记录 | Record(supplement)，可选填「因为看了《X》」 |
| 补录很久以前看过的一次 | 作品页 → 补录观影 | ViewingEvent（时间在前）→ 触发该 work 全部事件重排 |

**注意上表刻意不标注 first／rewatch。** 观看地点与初看／重看是两个独立维度，由时间顺序另行决定（见 §3.2）。「第一次影院观看、第二次在家重看」只是其中一种排列，不是模型。

## 5. 首页：鉴赏履历卡（用户第 2 点）

### 5.1 当前卡片

标题 + 感想原文前几行 + 状态点。信息密度低，与通用笔记软件的卡片没有区别。

### 5.2 新卡片结构

```
┌──────────────────────────────────┐
│ [海报]  《作品名》                 │  ← 海报左侧固定宽度（约 72px）
│         2026/08/03 (日) 19:20     │
│         TOHO シネマズ 新宿          │
│         [IMAX] [重看 · 第2次]      │  ← 徽章行
│                             喜欢 · │  ← 态度（已有）
└──────────────────────────────────┘
```

- **影院卡**：海报 + 完整场次信息 + 制式徽章 + 增强边框
- **线上卡**：海报 + 日期 + 「在家观看」 + 无制式徽章 + 普通边框
- **补充记录卡**：海报 + 「补充记录 · 距首次观看 3 年」，日期弱化

点击卡片 → 进入感想详情（保持不变）。

### 5.3 影院卡的「增强效果」（提案 C）

用户提到 Steam 头像发光边框的思路。我的建议是**让制式承载这个荣誉感**，而不是单纯加光效：

- 制式徽章做成「勋章」：`IMAX` / `Dolby Cinema` / `4DX` / `MX4D` / `ScreenX` / `爆音上映` / `应援上映` 各有配色
- 影院卡加**一层极细的金属质感描边 + 卡片顶部一道横向渐变高光**，不是整卡发光（整卡发光在深色壁纸上会糊）
- 高规格制式（IMAX / Dolby / 4DX）描边更亮；普通 2D 影院卡只有描边、无高光

理由：纯发光边框是通用的视觉装饰，任何 App 都能做；**制式勋章是电影院独有的、可收集的、有真实差异的东西**，更符合「个人记忆资产」的定位，也天然接上年度报告的「今年解锁了几种制式」。

严格遵守既有红线：不使用紫色、紫色渐变、玻璃拟态。

## 6. 作品书架与作品页（用户第 3 点）

### 6.1 侧边栏

首页顶部当前有三个图标（主题／搜索(禁用)／偏好设置）。新增一个抽屉入口，包含：

- **时间线**（当前首页，默认视图）
- **作品书架**（新）
- 偏好设置

### 6.2 作品书架

海报网格，每格：海报 + 作品名 + 「看过 N 次」角标。
分组／筛选：按 `work_type`（动画电影／真人电影／活动／其他）、按观看次数、按最近观看。

### 6.3 作品页（这是笔记软件做不到的那一页）

```
[大海报]
《作品名》 · 2026 · 动画电影
Bangumi 链接

── 观影履历 ──────────────
2026/08/03  TOHO 新宿 · IMAX · K-11  初看   ￥2,000  158分
2026/11/20  在家                      重看

── 评价变迁 ──────────────（提案 D）
初看：喜欢        →   重看：超喜欢

── 感想 ──────────────────
· 2026/08/03  影院观看后（3 张卡片）
· 2026/11/20  重看（1 张卡片）
· 2029/03/02  补充记录 · 多年后重评

[＋ 补充记录]
```

**「评价变迁」是这个 App 的护城河功能**：同一部作品在不同时间点的态度变化，只有把观影事件和作品资料分开、且长期积累的系统才能呈现。Obsidian、Notion、豆瓣都做不到（豆瓣只有一个覆盖式评分）。

### 提案 J：记忆卡片改竖向 —— 废止一条已冻结的规则

用户实测：横向滑动切换卡片"非常别扭、不自然"。手指的默认动作是顺着进度条竖向滑屏幕，横向分页与这个直觉相反。

**这条覆盖 `DEVELOPMENT_HANDOFF_V2.md` §5／§3 的「记忆卡片一次完整显示一张，不截断下一张」**——该规则是为横向分页写的。新规则：

> 记忆卡片竖向依次排列，自由连续滚动。下一张露出一角，作为"还有内容"的提示。

「露出一角」在竖向里不是缺陷而是**必要的可滚动性提示**，与原规则的立意（别让用户以为内容被切掉）其实一致，只是横竖两种方向的实现方式相反。

**结构性收益：** W8 要做的卡片上移／下移排序，只有在竖向布局里才说得通——横向分页里"上移"没有对应的空间隐喻。所以这一步也是 W8 的前置。

**风险与对策：** 竖向连续流动容易看起来像普通笔记 App 的列表。靠加大卡片间距、保留完整卡片边界、类型标签置顶来保住"一张一张"的卡片感。

### 提案 K：移除轮换壁纸 —— 一次做减法

用户实测结论：卡片铺满屏幕后壁纸基本看不到，功能没有兑现价值；日本几家主流影院 App 都没有把首页做成壁纸背景。

**判断成立，而且时机正好。** R3 引入海报后，视觉识别由海报承担；R4 的作品书架提供另一条浏览路径。壁纸的两项价值都被取代了。

**移除的连带收益比功能本身更大：** 首页不再有「壁纸 vs 文字对比度」这个长期约束，卡片设计彻底自由。原本纠结的「半透明卡片能不能做」（它同时撞上 §7 不透明规则和玻璃拟态禁令）**这个问题被整个消解掉了**，不需要再做 A/B。

**必须注意两处删除边界：**

1. **`apiBangumiImageUrl()` 与 Bangumi 图片代理要保留**——海报依赖它们，误删则海报全挂
2. **`wallpaperSettingsOverlay()` 不能整个删掉**——它同时承载云端同步、AI 偏好、数据导出等设置，只能改名为 `settingsOverlay()` 并摘掉壁纸区块

**一处必须补上：** 壁纸原本兼任「首次使用时首页不至于空荡」的角色。移除后要做一个真正的空状态（复用 C2 已有的原创二次元插画资产），不能留白屏。

### 提案 L：票务截图本地 OCR

用户担心的两点都有解，但真正的决定因素是第三点：

| 顾虑 | 实情 |
|---|---|
| 图片占空间 | 识别完直接丢弃、不持久化。正好符合现有的「票务原文不保存」红线 |
| AI 额度更贵 | 本地 OCR 零 API 成本 |
| **（更重要）隐私** | **把票务截图发给第三方 AI，等于把未脱敏的二维码、姓名、订单号整个传出去**，直接违反 §9 现有红线 |

现有架构的核心是「脱敏发生在任何处理之前，且全在本地」。服务端视觉 AI 会从根上破坏这条；本地 OCR 则与之完全一致。

方案：Tesseract.js，日语语言包约 3MB，**首次使用时才下载并缓存**，不进主 bundle。票务截图是清晰的屏幕渲染文字，是 OCR 准确率最好的场景。图片全程不出设备、不写入任何存储。

排到 **W13**，不进 R 阶段——它是增强，不是结构问题。R2 在粘贴区预留入口位置即可。

### 提案 M：纪念日开屏庆祝 —— 壁纸的正确替代

**这个思路比轮换壁纸强，强在稀缺性。** 每天都有的东西是背景噪音；一年只出现十几次的才是事件。壁纸失败的根本原因不是视觉做得不好，而是它每天都在。

#### 两种纪念日，一主一辅

| | 数据来源 | 可靠性 | 文案 |
|---|---|---|---|
| **观影纪念日**（主） | 本地 `ViewingEvent.viewed_on` | **100%，零外部依赖** | 「三年前的今天，你在 TOHO シネマズ 新宿 看了《XX》」 |
| **首映纪念日**（辅） | `Work.release_dates` | 有则显示，无则跳过 | 「《XX》在日本上映 5 周年」 |

观影纪念日是**关于你的事实**，首映纪念日是**关于作品的事实**。这个 App 的定位是「个人记忆资产」，所以前者为主。而且它零成本、零失败可能、离线完全可用。

#### 首映日期怎么来（要如实说明覆盖率）

- **日本上映日**：Bangumi 条目的 `date` 字段直接可得，覆盖率高。R1 匹配作品时**顺手存下来**
- **中国上映日**：Bangumi 一般没有。R4 的作品页提供手动填写入口
- Wikidata 的 `P577`（发行日期）带地区限定符，理论上可查中国上映日，但覆盖率不稳定。**留给 W14 自己评估，不作为前置依赖**

#### 呈现规则（用户已决策：开屏庆祝，一天最多一次）

- 海报全屏 + 一行文案，**点任意处立即消失**
- `meta.anniversary_shown_on` 记录当天日期，**一天最多出现一次**
- 只庆祝整周年（1 周年起），同年不算
- 无纪念日 → 什么都不显示，首页正常渲染
- **点海报可跳到该作品页**（R4）——让它成为一个入口，而不是一个死胡同

#### 撞车规则

同一天可能命中多个：

1. 观影纪念日优先于首映纪念日
2. 同类多个 → 取**间隔年数最多**的那个（越久越有分量）
3. 再并列 → 取个人态度更高的（超喜欢 > 喜欢）
4. 落选的不排队、不补显示——纪念日的价值在于稀缺，不在于全都看到

#### 为什么字段要在 R1 就加

`Work` 现在只有 `release_year`。等 W14 再补 `release_dates`，就要对全部存量 Work 再迁一次。R1 正在做迁移，**顺手多存一个日期几乎是零成本**。

与票价、活动字段是同一个道理：**数据尽早采，功能可以慢慢做。**

#### 一处不受影响

纪念日**不能替代首页空状态**。首次使用时既没有记录也没有纪念日，R3 该做的空状态照做。

### 提案 I 补充说明：活动为什么值得单独建模

用户常驻日本，与朋友一同参加影院活动是高频场景。**这个 App 首先是自用工具，其次才考虑开放。** 高频真实场景优先于通用性。

技术上更重要的理由：**活动信息晚做要多付一次数据迁移的代价**。字段在 R1 一并建好，几乎是零成本；等到 W9 再加，就要对全部存量 ViewingEvent 再迁一次。

**一个必须先厘清的区分——「制式」与「活动」是两类东西：**

| | 含义 | 例子 | 归属字段 |
|---|---|---|---|
| **制式** | 影厅硬件规格 | IMAX、Dolby Cinema、4DX、MX4D、ScreenX、2D | `viewing_context.format` |
| **活动** | 这一场的性质 | 舞台挨拶、応援上映、爆音上映、先行上映、特典配布 | `viewing_context.event_types` |

同一场可以既是 IMAX 又是舞台挨拶付き。当前 `ticket.js:extractFormatAndTitle` 把片名里的 `【...】` 前缀**一律当作制式**，所以 `【舞台挨拶付き】` 现在会被错误地存进 `format`。R1 需要按上表分流。

活动取值（`event_types`，多选数组）：

`stage_greeting` 舞台挨拶 / `talk_show` トークショー / `cheer_screening` 応援上映 / `roar_screening` 爆音上映 / `advance_screening` 先行上映 / `premiere` プレミア上映 / `revival` リバイバル上映 / `all_night` オールナイト上映 / `live_viewing` ライブビューイング / `bonus_distribution` 入場者特典 / `other_event` 其他

`bonus_distribution` 额外带一个自由文本 `bonus_note`（记「第几周特典是什么」），因为特典内容每周不同，枚举不了。

### 需要用户后续拍板、本次不做的两点

- **同行者字段**：既然常和朋友一起去，要不要记「和谁看的」？这会让年度报告多出一个维度（今年和谁看了几场），但也是这个 App 第一次引入他人信息，涉及隐私边界与导出策略。建议 R 阶段先不做，等履历卡和作品页跑顺了再单独决定。
- **搜索**：顶部搜索按钮目前是 `disabled`。作品书架上线后，搜索的价值会明显上升，建议排到 W12 之后单独一个窗口。
