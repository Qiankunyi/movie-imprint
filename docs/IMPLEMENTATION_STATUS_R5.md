# R5 · 作品资料层（系列 / 片单 / 一句话简介）与 R4 交互修复

本轮起因是用户实机试用后的 7 条反馈：前 4 条是交互与显示缺陷，后 3 条是新功能。
以下按反馈条目组织。

## 1. 侧边栏边缘手势又失效了 —— 根因：手势中途 render() 打断了触摸序列

上一轮补丁刚加的"从屏幕左边缘右滑打开侧边栏"，用户实测仍然拖不出来。

排查后定位到一个很具体的原因：原实现在 `touchmove` 里一旦确认是侧边栏手势，就立刻
`state.overlay = "sidebar"; render();`。而 `render()` 做的是 `app.innerHTML = ...`——
把整个 `#app` 重建一遍。`touchstart` 的目标元素（首页某张卡片）因此被销毁、从文档树里
脱离；触摸事件此后仍然派发给那个已分离的节点，但**不再冒泡到 `document`**，挂在
document 上的 `touchmove`/`touchend` 监听器就此收不到任何后续事件。表现正是用户说的
"拖动拖不出、交互无反应"——抽屉在确认的那一帧被挂上去，然后就永远停在那里不跟手，
松手也没有任何判定。

修复分三处：

1. **手势期间绝不 render()。** `index.html` 里新增一个 `#app` 之外的常驻 `#gesture-layer`。
   手势确认后把抽屉 HTML 塞进这一层跟手拖动，`touchstart` 的目标元素不会被销毁，事件
   链完整。只有在 `touchend` 提交时才真正切 `state.overlay` 并 `render()`——那时手指已经
   离开，重建 DOM 不影响任何事件序列。
2. **`touchmove` 改成非 passive 并在确认后 `preventDefault()`。** 否则 Chrome 会同时把这
   一滑当成页面纵向滚动处理，抽屉一边跟手一边被浏览器抢走。同时给 `body` 加
   `overscroll-behavior-x: contain`——安卓 Chrome 的左右边缘滑动默认是它自己的"后退/前进"
   导航手势，不 contain 的话边缘右滑会被浏览器整个吃掉。
3. **补齐手势的边界情况。** 新增 `touchcancel` 兜底（系统来电、手势冲突时抽屉不会卡在
   半开状态）；确认阶段先比较横纵位移，纵向更大就直接放弃，不跟页面滚动抢；遮罩透明度
   通过 `--scrim-progress` 逐帧跟手；提交/取消时都压掉 `drawer-in` 入场动画，避免松手瞬间
   从屏幕外重播一遍（看起来像"弹回去又滑出来"）。

点遮罩关闭也顺带统一成和右滑关闭同一条"先滑出去再摘 DOM"的动画。

## 2. 时间线卡片海报要占满上下左三边且不许变形

用户："为什么不能做到占满卡片的上下左三边的边沿，又维持正常的海报长宽比呢？"

这是同一处第四轮返工。前三轮一直在"固定宽度 + `aspect-ratio` 锁比例"上打转，最后停在
`align-self: flex-start`——比例对了，但卡片一旦比海报高，海报底部就空出一截背景色。

这轮的解法是把"盒子比例"和"图片比例"分开看：`object-fit: cover` 在盒子比例变化时是
**裁切**而不是拉伸，画面本身永远不会被压扁。所以让盒子放心地 `align-self: stretch`
占满卡片全高，图片交给 cover 适配即可：

- `.record-poster` 改 `align-self: stretch`、去掉 `aspect-ratio`，宽度固定 112px；
  卡片自身的 `overflow: hidden` + 圆角会自动把海报的左上/左下角裁好，不用单独写圆角。
- `.record-card-button` 的 `min-height` 设成 112 × 1.5 = 168px（标准海报 2:3），
  保证"内容较少"这个最常见情况下盒子恰好是 2:3，一个像素都不裁。
- 窄屏（≤370px）同步降到 96px / 144px。**这两个数字是一组的，改一个必须改另一个**，
  CSS 注释里已写明。

代价：内容极长的卡片上海报左右会被裁掉一点边缘。相比"底部空一截背景色"，这个代价
视觉上明显更小，也是各家票务/影视 App 的通行做法。

## 3. 态度标签完全没有区分度

原来五种态度共用同一套配色，"喜欢"和"不喜欢"长得一模一样，必须读文字才能分辨。

新增五组态度配色 token（浅色/深色各一套），冷暖分工：超喜欢偏暖金、喜欢用主色、
不喜欢偏红、无感灰、不好说用中性偏蓝的石板色（避开项目的紫色红线）。除了颜色，
圆点形状也做了区分，这样不依赖色觉也能分辨：

| 态度 | 圆点 |
| --- | --- |
| 超喜欢 | 实心点 + 外圈光环（并加粗字重） |
| 喜欢 | 实心点 |
| 无感 | 空心点 |
| 不好说 | 斜切半填充 |
| 不喜欢 | 压扁成一道横杠（"减号"） |

## 4. 上映日不能预设地区

用户：《蜘蛛侠：崭新之日》抓到的 7 月 29 日在 Bangumi 上标的是中国上映，系统却当成
日本上映。

根因确认：`promoteWorkToMatched` 把 Bangumi 的 `subject.date` 直接写进
`release_dates.jp`。但 Bangumi 的 `date` 字段**不带地区语义**，这个假设从一开始就不成立。

数据结构改成「日期 + 地区」的条目数组：

```js
release_dates: {
  entries: [{ id: "cn_2026-07-29", region: "cn", date: "2026-07-29", source: "bangumi" }],
  jp: null, cn: null, other: []   // R1 旧字段保留为空，仅为兼容过渡
}
```

- 地区取值：日本 / 中国大陆 / 中国香港 / 中国台湾 / 美国 / 其他地区 / **未标注地区**。
- 抓取回来的日期一律落 `region: "unknown"`，在作品页上用暖色高亮显示「待认领」，
  点开就能用下拉认领是哪个地区——这正是这类错标问题的可见入口，不能做成一个和其他
  chip 一样安静的灰块。
- 同一部片可以有任意多条上映日（不同地区上映日不同是常态），全部可手动增删改。
- 作品的显示年份改成取**最早**的一条上映日，不再从写死的 `release_dates.jp` 读。
- `mergeWorks` 合并重复作品时，上映日从"同一槽位二选一"改成"条目取并集"，
  两边各自标注的地区都保留，不会因为合并而丢失。

存量数据由迁移（`MIGRATION_VERSION` → `r5-library`）把旧的 jp/cn/other 归一化进 entries。

## 5. 系列（Series）：独立实体

按用户确认的方案（并采纳了用户转述的 Gemini 分析），系列做成**独立实体 + 关联**，
而不是作品上的一个字符串字段：

```js
// store: series
{ id, title, aliases, external_refs, member_ids: [...有序], relations: [...], created_at, updated_at }
```

关键设计决策——**抓取只留锚点，关系标签靠手动**：

> Bangumi 的关系树结构复杂且易变，爬虫强行解析容易报错。所以抓取只负责把关联条目的
> ID 存进 `work.related_refs` 当锚点，「前作/续作/外传/平行世界」这类中文关系标签
> 完全交给用户在系列页上手动连线。

- 关系类型：前作 / 续作 / 番外 / 外传 / 平行世界（另一版本）/ 总集篇 / 重制 / 其他关系。
- 关系是**有向的，且不自动写反向**——"A 的续作是 B" 不等于用户想同时声明 "B 的前作是 A"，
  让用户自己决定要不要两边都连（和 Bangumi 的做法一致）。
- 系列内顺序由 `member_ids` 的数组顺序决定，系列页上可逐项上移/下移。顺序含义
  （上映顺序？观看顺序？故事时间线顺序？）刻意不规定，由用户自己定。
- 一部作品只能属于一个系列：归入新系列时会先从原系列移出，否则同一部作品会同时出现在
  两个系列的成员表里，顺序与关系都失去意义。
- 从系列里移除某部作品时，**连带清掉它参与的所有关系连线**，不留悬空关系。

新增系列页（`#series=<id>`），入口在作品页的「系列」行。

## 6. 片单（Collections）：用户自定义主题列表

参考豆瓣片单：

```js
// store: collections
{ id, title, description, work_ids: [...], created_at, updated_at }
```

- 与系列**正交**：系列描述"作品客观上属于哪个系列"（一部作品只属于一个），
  片单描述"我出于自己的用途把哪些作品归在一起"（一部作品可属于多个）。
  这句话也直接写进了片单编辑面板的说明文案里，避免用户混淆这两个概念。
- 片单标题允许重复（"2026 年度私选"这种名字用户可能真的会建两个），所以 id 带时间戳，
  不像系列那样按标题去重。
- 新增片单列表页（`#collections`）与片单详情页（`#collection=<id>`），侧边栏加了入口；
  作品页的「片单」行可以直接勾选加入/移出，或新建片单并加入。

## 7. 一句话简介：抓取优先 → AI 兜底 → 手动可改

按用户确认的方案实现，三种来源在 UI 上可分辨（存成 `{ text, source, updated_at }`）：

1. **抓取优先**：匹配 Bangumi 时从 `summary` 抽第一句。抽不出、或第一句超过 48 字，
   一律返回 null 而**不硬截断**——截出来的半句话比没有更糟。
2. **AI 兜底**：作品页「一句话简介」编辑面板里有一个「让 AI 概括一句」按钮，**手动触发**，
   不在匹配作品时自动跑（避免每匹配一部电影就静默消耗一次 AI 额度）。新增
   `functions/api/ai/tagline.js` 与 `requestAiTagline()`。
   - 只发送作品的公开信息（标题/原名/年份），**不发送用户的感想原文**——这里要的是
     作品客观介绍，把私人记录发出去既没必要也不合适。
   - Prompt 明确要求：只写"讲了什么"，不写评价、不写推荐语、不剧透结局；不确定这部
     作品时返回空字符串而不是编造剧情。
   - AI 结果只填进输入框，**不直接落库**，用户看过并点保存才算数——和 App 里其余
     AI 产出的处理方式一致，也和"AI 不替用户写"这条核心红线一致。
3. **手动可改**：任何时候都能直接编辑覆盖，来源标记会变成"手动填写"。

# R5 补丁 1：实机测试后的 6 项修复

用户实机测试后反馈 6 个问题，其中若干是我前一轮做错/理解错的，逐条记录根因。

## 1. 右滑手势仍然打不开侧边栏 —— 两个错误叠在一起

**错误一：需求理解错了。** 我一直把它做成"必须从屏幕最左边缘起手"的 edge-swipe。
用户澄清：要的是**在画面中间随便哪儿从左往右一划就能拉出抽屉**，跟边缘无关。

**错误二：就算按边缘手势做也不可能生效。** 安卓（尤其小米 HyperOS）把屏幕最左侧约
20–24dp 划给**系统返回手势**，落在那条窄边里的触摸由系统消费，网页根本收不到
touchstart/touchmove。我前两版把识别区设成 24px / 28px，整个识别区都躺在系统手势区
里面——代码逻辑再对也永远不会被触发。识别区越贴边，越是必然失效。

现在两个问题一起解决：

- 取消起手位置限制，屏幕上任意位置（只排除最右 8%，留给系统前进手势）横划都能拉出抽屉。
- 误触由两道判定挡住：横向位移必须先超过 16px，且必须是纵向位移的 1.5 倍以上
  （斜着滚页面不会误触）；起手点若在横向可滚动容器里（徽章行等）则让位，不抢手势。
- 松手判定改成固定 90px 位移，不再按抽屉宽度取比例——从画面中间起手时，
  "划过抽屉宽度的 35%" 这个尺度并不直观。

上一轮已修的"手势中途 render() 打断触摸序列"仍然保留（`#gesture-layer` 那套）。

## 2. 海报左边被裁掉

上一轮用 `min-height` + `object-fit: cover`：卡片被长内容撑高后盒子就不再是 2:3，
cover 于是从左右各裁掉一块——正是用户看到的"左边被裁掉一部分"。

这三个要求（占满上下左三边 / 完整显示 / 比例不变）只有在**卡片高度被钉死**时才能同时成立：

- `.record-card-button` 改用固定 `height: 168px`（= 海报宽度 112 × 1.5），不是 min-height。
- `.record-card-body` 加 `overflow: hidden`，内容再多也不许撑高卡片。
- `.record-poster-img` 从 `cover` 改成 **`contain`**：保证整张海报完整可见且永不拉伸。
  万一某张图源不是标准 2:3，contain 只会留一点点两侧留白，而不是裁掉画面——
  按用户明确的优先级（完整 > 铺满每一寸），留白可接受，裁切不可接受。
- 窄屏同步改成 96px / 144px。**这两个数字必须成对修改**，CSS 注释里已写死这条约束。

## 3. 书架筛选标签右端被截断

原实现是 `overflow-x: auto` 横向滚动，窄屏下最后一个 chip 正好卡在容器边缘，
看起来像被切掉，而且用户根本不知道这行还能横着拨。

要求是**严格两排、全部标签同时完整可见**——横向滚动（有东西藏在屏幕外）和自动换行
（会变成三四排）都不满足。所以这里是把标签样式重新设计成能塞进两排：

- 行容器 `flex-wrap: nowrap`，不滚动也不换行。
- chip 的内边距、字号、行内间距全部改用 `clamp()` 跟着视口宽度收缩
  （字号 11–12px、内边距 6–12px、间距 4–8px），窄屏自动变紧凑，
  但 `white-space: nowrap` 保证文字始终完整，不出省略号。
- 排序标签改用用户自己的说法：**最近观看 / 最多观看 / 首次记录**
  （原来的"观看次数""首次记录时间"更长，第二排在窄屏塞不下）。

按上述参数验算过 320 / 360 / 393 / 412px 四档宽度，两排都有余量：
最窄的 320px 下第一排 272/288px、第二排 271/288px。

## 4. AI 一句话简介"点了没反应" —— 我把这个功能理解错了

用户要的流程是：**先抓取作品的完整简介 → 简介显然超过一句话 → AI 把这段简介压缩成
一句话 → 用户觉得不合适再手动改**。我上一版只把片名发给 AI，等于让模型凭印象自己编
一句介绍，这既不是用户要的，也容易编造剧情。加上失败提示只写进了 `announce()`
（屏幕阅读器专用的隐藏区域），看得见屏幕的用户点了按钮完全没有任何可见反馈。

改动：

- 新增 `functions/api/bangumi/subject.js`，按 subjectId 拉条目详情拿**完整 summary**
  （搜索接口给的 summary 有时是截断的，历史上已匹配的作品当时更是压根没存）。
  拿到后写回 `work.summary`，下次不用再请求。
- 打开「一句话简介」面板时自动取简介原文，并在面板里以可展开的形式**显示出来**，
  用户能看到 AI 到底在概括什么，不是一个黑盒按钮。
- `requestAiTagline()` 现在**必需** summary 参数，prompt 也改成"压缩这段给定的简介，
  不要引入原文里没有的内容"；缺 summary 直接返回 400 并说明原因。
- 用户列出的"不需要 AI"的两种情况已经覆盖：简介本来就一句话、或第一句就合适时，
  `taglineFromSummary()` 会直接把输入框填好，用户看一眼保存即可，完全不动 AI。
- 所有成功/失败反馈改用可见的 `showToast()`；AI 未配置、简介没抓到、正在加载这三种
  情况会禁用按钮**并在旁边写明原因**，不会再出现"点了没反应"。

（用户提到的"抓取高热度短评"这条暂未实现——Bangumi 的评论接口没有稳定的"热度"排序，
硬做容易抓到噪音。目前留在简介概括这条路径上。）

## 5. 系列和片单两行没对齐

系列那行的值是纯文本、片单那行的值是带边框内边距的 chip，两者文字起点自然差一截。
现在两行共用同一个两列网格（固定标签列 + 值列），值也统一成同一种 chip 样式。

## 6. 上映日删除按钮点了没反应 —— 真 bug

根因在 `normalizeReleaseDates()`：它把旧的 `jp`/`cn` 搬进 `entries` 之后，**又把
`jp`/`cn` 原样保留在返回值里**。于是 `removeReleaseDate()` 从 entries 里删掉的条目，
在下一次 `normalizeReleaseDates()` 调用时又被 `jp`/`cn` 复活回来——表现就是点删除
完全没反应。这同时也解释了用户截图里"同一个 2026/07/29 既是日本又是中国大陆"的重复条目。

修复：归一化后一律清空 `jp`/`cn`/`other`（它们已经完整搬进 entries，保留就是有害的）。
另外补上此前缺的能力：**日期本身也可以直接编辑**，不再是只能改地区、只能新增。
增删改三个操作现在都有可见的 toast 反馈。

新增回归测试锁住这个 bug：删除一条之后再归一化一次，不能又冒出来。

# R5 补丁 2：侧边栏闪屏 + 时间线卡片按 EhViewer 重做

## 1. 拖出侧边栏时不停闪屏

根因在 CSS 选择器：

```css
/* 错误写法 */
.sidebar-overlay[style*="--scrim-progress"] .overlay-backdrop { animation: none; }
```

`--scrim-progress` 是手势期间**每帧都在改写**的内联属性，而这个属性子串选择器
依赖 style 属性的序列化结果。属性每变一次，选择器就要重新匹配一次，
`animation` 在 `scrim-in` 与 `none` 之间反复切换 → 入场动画被不断取消又重启，
表现就是拖动时整个遮罩不停闪。

修复三处：

- 拖动态改用稳定的 `.is-dragging` 类标记，CSS 据此关掉入场动画与过渡；
  样式属性怎么变都不会再影响选择器匹配。
- 手势期间的样式写入用 `requestAnimationFrame` 合并到一帧
  （touchmove 触发频率可能高于刷新率，逐事件直接写样式会造成同帧内反复读写抖动）。
- 抽屉插入 DOM 后**在同一个同步块里**立刻打上 `.is-dragging` 并置为 `translateX(-100%)`，
  避免先播一帧 `drawer-in` 入场动画（那也是一次可见的闪烁）。

顺带把手势代码里对 `overlay-open` 类的增删去掉了——全项目没有任何 CSS 规则用到这个类
（`render()` 里那处历史调用保留未动，它同样是空操作，但不属于本次改动范围）。

## 2. 时间线卡片按 EhViewer 的安卓卡片重做

用户指定的排布（参照 EhViewer，用户给出具体改造思路）：

```
┌──────────┬────────────────────────────┐
│          │ 作品标题（固定占两行）        │
│  海报     │ 影院名  [制式徽章][活动徽章]  │
│  原图比例 │ ⟨态度标签⟩                  │
│  占满三边 │                  观影日期 ↘ │
└──────────┴────────────────────────────┘
```

- **直角，去掉圆角**（用户原话："我们是高贵的安卓"）。圆角还有个实际害处：
  海报是矩形，卡片圆角会把海报四角切掉一小块画面。
- **标题固定占上方两行**（`-webkit-line-clamp: 2` + `min-height`），
  不足两行也保留两行高度，卡片之间的信息位置才对得齐。
- 影院名（非影院时是"线上观看"/"在家观看"等），**右边同一行接制式/活动徽章**。
- 态度标签在影院名下方；票根尖角**从左端移到右端**
  （`clip-path` 改成 `polygon(0 0, calc(100% - 8px) 0, 100% 50%, calc(100% - 8px) 100%, 0 100%)`），
  左边变平，正好和影院名那一列的左对齐线对齐。
- 观影日期钉在**卡片右下角**（`margin-top: auto` + `text-align: right`）。

### 海报：原图比例、占满三边、零裁剪零留白

这一项前后返工了五轮，最后按用户的决断解决："如果爬取的原图大小不统一，
那就让卡片上的海报宽度不一"。这三个约束（原图比例 / 上下左占满 / 不许裁剪或留白）
同时成立的唯一办法就是**让宽度随图变**：

```css
.record-card-button { height: 180px; }          /* 卡片高度固定 */
.record-poster      { flex: 0 0 auto; align-self: stretch; }  /* 宽度不写死 */
.record-poster-img  { height: 100%; width: auto; aspect-ratio: auto 2 / 3; }
```

高度撑满卡片、宽度 `auto` → 浏览器按图片**自身的宽高比**算出宽度。
于是不同图源的海报宽度会不一样，这是预期行为。
`aspect-ratio: auto 2 / 3` 表示"有原生比例就用原生的，还没加载出来时按 2:3 预留"，
避免图片加载完成瞬间卡片宽度跳变。

配套改动：有海报时**只渲染 `<img>`**，不再在它下面叠一层占位块——
图片必须参与正常布局才能用自身比例撑出宽度，不能 `position: absolute`。
只有在没有海报时才渲染标准 2:3 的首字占位块。

卡片高度 180px 是按内容实测算出来的：标题两行 52 + 影院行 18 + 态度 28 + 日期 18
+ 三个间隙 24 + 上下内边距 24 = 164px，180 有余量；窄屏（≤370px）降到 168px。
