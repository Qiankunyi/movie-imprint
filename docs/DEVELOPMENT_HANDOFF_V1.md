## 1. 开发目标

开发一个移动端优先、可安装到 Android 手机主屏幕的私人 Web／PWA 工具：用户写下或粘贴真实电影感想，系统安全保存原文，由 AI 生成有证据的结构化草稿，用户确认后保存、导出并按需同步至 GitHub。

它不是影评写作器、评分网站、电影百科、AI 聊天机器人或公共社区。

第一阶段面向单个核心用户，但数据模型不能把用户身份永久写死。

## 3. 不可改变的 MVP 边界

### 3.1 默认作品范围

- 动画电影；
- 真人电影。

### 3.2 有限例外

可从次级入口记录：

- 影院 TV 动画先行上映；
- 若干集影院连映；
- 影院特别放映。

特别放映必须发生在线下影院／实体活动，并记录作品名及集数范围或自由放映说明。

不得因此加入：

- 家庭 TV 动画观看；
- 季度追番；
- 进度管理；
- 逐集日记；
- 电视剧、游戏、漫画或小说。

### 3.3 明确不做

- 数字评分、星级与排行榜；
- 自动抓取豆瓣、微博、Bangumi 用户内容；
- 公共社区和多用户社交；
- 自动发布到博客或社交平台；
- 复杂统计和关系图谱；
- 图片、票根和特典附件；
- GitHub 文件与应用之间的复杂双向合并；
- AI 自动把原文重写成长评。

## 4. 核心用户流程

```text
记录一部电影
  → 输入电影名和原始感想
  → 可选观看地点
  → 电影院时可粘贴票务邮件
  → 本地保存原文草稿
  → AI 生成结构化建议
  → 用户确认或修改
  → 预览并保存正式记录
  → 按需导出或同步 GitHub
```

必须提供的逃生路径：

- 无网络：保存本地草稿，稍后分析；
- AI 失败：重试、返回编辑或只保存原文；
- 不想整理：直接保存仅原文正式记录；
- 条目搜索失败：按当前输入创建本地作品；
- 票务解析失败：保留感想，手工确认少量可识别字段；
- GitHub 同步失败：本地正式记录不受影响。

## 5. 数据模型基线

顶层实体：

1. `Work`：作品；
2. `ViewingEvent`：一次实际观影／放映；
3. `ImprintRecord`：一次感想表达；
4. `RawLayer`：用户原文及修订；
5. `ImprintLayer`：态度、情绪、记忆卡片；
6. `ActionLayer`：后续关系与推荐。

关键关系：

- 一个作品可有多个观影场次；
- 一个作品可有多条感想记录；
- 一条感想可关联零个、一个或多个观影场次；
- 一次重看建立新的场次和新的感想，不覆盖旧记录；
- 后续补充可以没有新的观影场次；
- 原始层、AI 草稿和人工确认结果必须分开保存。

精确字段和枚举以《字段与标签冻结》为准，不在开发时随意增加顶层字段。

## 6. 结构化模块基线

### 6.1 个人态度

严格保持五项：

- 超喜欢；
- 喜欢；
- 无感；
- 不喜欢；
- 不好说。

仅原文记录可以不选择态度。

### 6.2 情绪

- 46 个预设标签；
- 分组呈现；
- AI 通常只建议 3–7 个；
- 用户可删除或自定义；
- 不在一个页面平铺完整标签库。

### 6.3 记忆卡片

- 44 个预设类型；
- 添加时先进入类型库，再出现模板；
- 支持搜索、分组和最近使用；
- 卡片可编辑、删除、改类型、排序、关联场次和标记核心；
- 不要求每种类型都出现；
- 新需求优先使用自定义卡片，不立即扩充系统枚举。

### 6.4 后续关系与推荐

- 后续关系以用户选择为主，AI 不自动确认；
- 推荐只有“会／看对象／不会”，整项可留空；
- AI 不从感想文本推断“会／看对象／不会”；推荐值必须由用户主动选择；
- 用户选择后，AI 只可依据原文协助整理推荐对象、理由、注意事项或不推荐原因，没有依据时保持空白；
- 喜欢程度、推荐意愿和后续行为相互独立。

## 7. AI 输出硬规则

AI 必须：

- 只根据用户原文分析；
- 原文没有的信息返回空值；
- 每个态度、情绪、卡片和推荐建议提供原文证据；
- 区分明示与推测；
- 区分用户自己的声音、引用他人和来源元数据；
- 区分直接感受、观察、解释和转述；
- 保守处理复杂态度；
- 返回固定结构；
- 所有结果先处于待确认状态。

AI 不得：

- 覆盖或润色原文；
- 用网络口碑代替用户感受；
- 补造观看经历；
- 为填满字段而生成内容；
- 把他人原话写成用户态度；
- 把“据说”改写成已核实事实；
- 自动保存、导出、同步或公开发布。

票务解析与感想分析必须是两个任务。票务邮件不能拼接进感想提示词。

## 8. 票务导入与隐私

处理顺序：

```text
浏览器本地拆分消息
  → 浏览器本地移除敏感信息
  → 确定性模板解析
  → 必要时才用 AI 补充非敏感字段
  → 用户确认
  → 建立一个或多个 ViewingEvent
```

默认不得保存、发送给 AI、导出或同步：

- 姓名；
- 邮箱和手机号；
- 订单号；
- 取票码；
- QR 地址和令牌；
- 会员入口；
- 票价、票种和支付信息；
- 原始票务邮件。

多封邮件必须：

- 先按消息边界拆分；
- 再按实际时间排序；
- 不因同日、同影院、同制式而合并不同作品；
- 当前作品以外的有效场次可保存为“待写感想”。

## 9. 条目匹配

交互：

1. 用户自然输入自己记得的片名；
2. 同时查询本地已有作品与外部条目；
3. 最多展示三个候选；
4. 用户一键确认或忽略；
5. 始终可以按当前输入创建本地作品。

数据源：

- Bangumi 正式 API 是首个自动搜索来源；
- Bangumi URL 可直接绑定 ID；
- 豆瓣 URL 可保存豆瓣 ID；
- 不抓取豆瓣页面作为产品依赖；
- 真人电影覆盖不足时，由开发窗口提出具有正式接口的备选数据源，不得擅自接入不稳定爬虫。

## 10. 导出与 GitHub

### 10.1 导出

- JSON 是结构化基准；
- Markdown 和 TXT 由同一份正式数据生成；
- 三者必须包含完整原文；
- 未填写字段不能用虚构内容补齐；
- 使用 UTF-8、ISO 8601 时间和稳定 ID。

### 10.2 仓库

- `movie-imprint`：公开源码与产品文档；
- `movie-imprint-records`：默认私有的个人记录资产。

个人令牌和私人原文不能进入公开仓库。真实验证样本不得原样随源码发布。

### 10.3 同步

- 只有正式保存后才能同步；
- 必须由用户主动点击；
- 同步前显示仓库与路径；
- 同步失败不回滚本地记录；
- GitHub 首要角色是长期备份与可阅读存档，不是 MVP 的实时协作数据库。

---

## 11. 视觉设计是一项前置验收，不是开发自由项

必须完整遵守《视觉设计方向与前端验收规范 v1》。一句话基线：

> 以 2023 Chrome Material You 的克制蓝灰气质为视觉参照，以当前 Material Design 3 和 Android 规范实现；不得使用 Material baseline 默认紫色、紫色渐变或通用 AI SaaS 模板。AI 是安静的后台整理能力，用户原始感想才是界面主角。

### 11.1 开发顺序闸门

在批量开发前端页面之前，开发窗口必须先完成：

1. 颜色、字体、圆角、间距、阴影和状态 tokens；
2. 首页、新建电影、票务确认、AI 确认工作台、卡片类型库、最终预览六个关键页面的 Android 手机视觉样张；
3. 首页、新建电影和确认工作台的深色样张；
4. 360×800 小屏检查；
5. 中文／日文真实内容混排；
6. 正常、选中、错误／离线等状态。

提交样张给用户／设计窗口确认。没有通过，不继续批量实现其余前端。

### 11.2 一票否决

- 默认紫色、蓝紫色或洋红色主色；
- 紫蓝／紫粉渐变；
- Material baseline 默认紫色主题；
- 玻璃拟态、霓虹和发光；
- 通用 AI SaaS 模板；
- 桌面后台布局压缩到手机；
- 每个区块都是同一种圆角白卡片；
- AI 星光、机器人或聊天气泡压过用户内容；
- 长文本字号小、行距挤；
- 只做浅色、不做深色。

## 12. 移动端与 PWA 基线

- Android 手机竖屏是第一界面；
- 可以添加到主屏幕；
- 支持弱网与离线原文草稿；
- 页面切后台和意外关闭后可恢复；
- 支持 edge-to-edge，但内容与控件避开系统栏和手势区；
- 触控目标最低 48×48dp；
- 正文默认约 16sp，不小于 12sp；
- 支持系统字体缩放；
- 文字对比度至少 4.5:1，非文字关键元素至少 3:1；
- 不依赖颜色单独表达状态。

---

## 13. 开发窗口需要提出、但不能默默替用户决定的技术事项

第一阶段技术方案必须逐项给出推荐、理由、成本和替代方案：

1. Web／PWA 框架与语言；
2. 部署平台；
3. 单用户登录与会话保护；
4. 应用数据库及数据主副本关系；
5. 本地草稿、离线队列与恢复机制；
6. AI 服务端代理、模型选择、结构化输出和成本控制；
7. GitHub OAuth／授权方式及令牌存储；
8. Bangumi API 缓存、限流与降级；
9. 数据迁移与 `schema_version` 策略；
10. 自动化测试、隐私测试和部署检查。

产品层当前倾向“应用数据库作为日常主存储＋GitHub 作为用户拥有的结构化备份”，但开发窗口应在技术方案中验证，不得未经说明改成 GitHub-only 或浏览器-only。

## 14. 推荐开发阶段

### 阶段 A：技术方案，不批量写页面

交付：

- 技术架构建议；
- 数据流与安全边界；
- 仓库和目录规划；
- 待用户确认的技术选择；
- 风险与降级方案。

### 阶段 B：视觉基线

交付：

- design tokens；
- 六个关键页面视觉样张；
- 浅色、深色和小屏检查；
- 视觉验收清单逐项说明。

必须得到确认后进入下一阶段。

### 阶段 C：最小纵向切片

只先跑通：

```text
首页 → 新建电影 → 本地草稿 → 只保存原文 → 记录详情
```

目的：先验证手机输入、草稿安全、数据模型和视觉实现。

### 阶段 D：AI 整理与确认

加入：

- 固定结构化输出；
- 五项态度；
- 情绪；
- 记忆卡片；
- 证据与用户确认；
- 失败重试与仅原文降级。

### 阶段 E：电影专属能力

加入：

- 观看场景；
- 票务脱敏与解析；
- 多场次；
- 影院特别放映；
- 重看与后续补充。

### 阶段 F：导出与 GitHub

加入：

- JSON／Markdown／TXT；
- 私有数据仓库连接；
- 主动同步；
- 同步状态和失败恢复。

## 15. 验证样本使用方式

开发阶段至少覆盖：

- 零散但正向的《大雄与云之王国》；
- 极强喜欢的《链锯人 蕾塞篇》；
- 不喜欢但仍有亮点的《你与烟花与约定》或《新·海底鬼岩城》；
- 多影院制式比较的《曼达洛人与古古》或《魔女宅急便》；
- 发散、引用他人且带个人背景的《二十世纪电气目录》；
- 脱敏后的 SMT 两封连续票务结构。

验证关注行为和数据，不要求公开原始私人内容。公开测试夹具应使用人工合成或充分脱敏文本。

## 16. MVP 完成定义

只有同时满足以下条件才算完成：

- 手机端可顺畅记录，原文不会因断网或 AI 失败丢失；
- 用户可以仅保存原文；
- AI 建议均有证据并等待确认；
- 五项态度、46 个情绪和 44 个卡片类型按冻结规则工作；
- 普通电影和影院特别放映边界正确；
- 多次观看和多场次关联不复制原文；
- 票务敏感信息不进入 AI、日志、导出或 GitHub；
- 三种导出来自同一份正式数据；
- GitHub 同步由用户主动触发；
- 浅色、深色、Android 小屏和无障碍状态通过检查；
- 前端通过视觉验收，不呈现默认紫色或 AI 模板感；
- 公开源码仓库不包含令牌和私人验证原文；
- 关键选择、数据结构和运行方式有文档。
