## 二、核心功能复盘：AI 建议卡片（记忆卡片）

这是你现在觉得"弱智"的部分。先把当初的设计意图完整还原，再对比现在代码实际在做什么，差距非常清楚——而且**项目自己在 R6 状态文档里已经承认了这个问题**，只是没有处理。

### 2.1 最初的产品设计意图

产品定义文档（§5.1）对卡片的定位说得很清楚：

> "记忆卡片是'电影印记'的核心结构，不是要求全部回答的问卷。AI 根据原文只生成实际有内容的卡片……每张卡片只表达一个主要记忆点；同一类型可以有多张。"

§6.1 明确划定 AI 的职责边界：AI 应该做的是——把用户零散写下的感想**拆分成记忆卡片**、提取有证据支撑的情绪反应、区分"用户自己的感受"和"用户的推测"和"转述他人的说法"三种不同性质的内容。AI **不应该做**的事：润色、摘要或重写原文；替用户填充结构；为了凑覆盖率生成原文没提到的卡片类型。

关键的一条设计原则（§6.8）：

> "相似卡片应合并，避免同一原文片段产生多张近义卡片；明显独立的多个点必须分开，不能压缩为一张综合影评卡片。"

也就是说，AI 的核心工作不是"切句子"，而是**判断哪些内容在情感/因果上属于同一个记忆点该合并，哪些看似相似但其实是用户分别记住的独立瞬间该保留**。这是一个需要理解语义的判断动作，不是格式化动作。

卡片本身设计了 12 个字段（§5.2），其中除了 `content`（记住了什么），还有 `why_it_matters`（为什么记住、为什么对自己重要）、`related_emotions`（关联情绪）、`linked_viewing_ids`（关联到哪次观影）——这些字段是把卡片从"一段摘录"升级为"一份带着理解的记忆"的关键。

### 2.2 分类体系设计

`FIELD_AND_TAXONOMY_FREEZE_V1.md` 冻结了完整的分类框架：**46 个情绪标签**（分 7 组：愉悦体验、强烈触动、消极体验、认知反应、持续感受、沉浸状态、交流冲动）、**44 种记忆卡片类型**（分 8 组：故事与表达、人物与表演、视觉与演出、声音与音乐、个人反应、关联与语境、影院与现场体验、自定义）。文档特别注明"AI 通常只建议 3-7 个，用户不会在首屏看到完整列表"——说明当初设计者已经考虑到了展示层面要克制，问题不在于展示数量，而在于底层这套丰富的分类体系有没有被真正用起来。

### 2.3 当初验证案例展示的"好"标准

`docs/validation/CASE_001_DORAEMON_SHORT_REVIEW.md` 是当初为了验证 AI 能力做的一个具体案例，里面完整写出了 AI 应该如何做合并/拆分判断，比如：

- 把"核威慑被利用"和"哆啦A梦亲手毁掉云之王国"两个情节点**合并**成一张卡片，理由写明："这一段保留为一张卡片，因为二者在原文中构成同一条因果链，拆成两张会割裂用户被打动的原因。"
- 两个都是"可爱/有趣的瞬间"类型的片段**不合并**，理由："用户分别记住了两个独立场景，合并会损失原始清单式感想的颗粒度。"

案例文档自己总结出的产品规则里明确写着："卡片数量不能预设上限，未来长评应通过合并重复观点控制数量，而不是机械截断。"

这份案例文档清楚地展示了当初想要的效果：**一次真正带着理解的分析过程**，而不是逐句切分。但值得注意的是，这类"长评/多观点合并"的复杂验证场景（`VALIDATION_DATASET_V1.md` 里设计的 12 个案例）在 CASE_001 里被标注为"下一案例要验证的问题"，之后却没有留下对应的验证报告——唯一存在的 `AI_VALIDATION_REPORT_C3.md` 测的是 7 个短句级别的态度分类边界场景（比如"明确喜欢""喜欢与不满交织""转述他人观点"），从未真正测试过合并/拆分判断这个核心能力。也就是说，这个案例定义的标准写出来了，但从未被真正验证过、也没有被写进实际系统提示词。

### 2.4 当前实现：实际发生了什么

现在真正发给模型的系统提示词（`src/ai.js` 的 `AI_SYSTEM_PROMPT`）里，唯一涉及卡片粒度的是第 4 条规则："一张记忆卡片只整理一个独立记忆点；不要把多个点压成综合影评"——这条规则只讲了"不要过度合并"，完全没有提到"相似卡片应该合并"这一半，更没有给出 CASE_001 那样的具体判断示例。整份提示词里没有任何一句话要求模型去做"分析、提炼"，用的动词始终是"整理"。

输出的 JSON Schema 也被大幅简化：

- 情绪部分只有 `{label, evidence, confidence}`，没有 `tag_id`、没有分组、没有跟 46 个冻结标签的枚举关联——情绪现在完全是自由文本，代码里搜不到任何 `EMOTION_TAGS` 这样的常量。
- 卡片部分没有 `related_emotion_tag_ids`（关联情绪）、没有 `linked_viewing_ids`（关联观影记录）、没有 `custom_fields`——这三个当初设计好用来把卡片串联成"记忆网络"的字段，在代码里完全不存在。
- 卡片类型枚举只有 16 个（`src/domain.js` 第 653 行），是冻结的 44 种里挑出来的一个子集，缺了"剧情转折/结局""设定世界观""改编处理""创作者幕后""最想长期记住""系列联系"等 28 种。
- `maxItems: 7` 的硬上限直接写进了 schema 和校验逻辑——这正好违反了 CASE_001 案例总结出的产品规则"卡片数量不能预设上限"。

更值得注意的两点：

1. **`why_it_matters` 字段被生成、被校验，但从来没有在界面上展示或编辑过。** `memory-list.js` 渲染卡片时只用了 `type`、`title`、`content`、`evidence` 四个字段，`app.js` 的卡片编辑浮层表单里也没有这个字段。也就是说，当初专门设计来承载"为什么这对你重要"这层分析的字段，AI 生成完之后直接被界面丢弃了。
2. **重新生成按钮没有记忆。** 点"AI 重新整理"时，调用的是同一个接口、同一段提示词、同样的原文，返回的新卡片直接拼接到已有卡片列表后面（`record.cards = [...record.cards, ...newCards]`），模型完全不知道已经生成过哪些卡片，所以没有任何机制避免同一段原文重复生成相似卡片。

无 AI 时的本地兜底逻辑（`src/domain.js` 的 `deterministicAnalysis()`）问题更直白——就是按标点分句，取前 3 句长度≥6 字的句子直接当卡片内容，没有任何分析，这个本来只是"离线兜底"的实现，恰好和现在被诟病的 AI 路径在精神上是一回事。

### 2.5 项目自己已经写下的诊断

`IMPLEMENTATION_STATUS_R6.md`（第 986-996 行）里已经原话记录了这个问题，值得完整摘录：

> "用户反馈：AI 生成的卡片只是把感想原文机械切分转抄成几张，没有做分析与提炼，不构成'整理成更好的记录'。这与产品定义里'AI 并非先替用户写影评，而是先帮助用户整理记忆素材'的目标有差距——当前实现更接近'分段'而不是'整理'。本轮未处理，相关代码在 `functions/api/ai/analyze.js` 与 `src/ai-providers.js`（提示词与卡片结构），以及 `src/domain.js` 的 `deterministicAnalysis()`（无 AI 时的本地兜底，目前就是按句切分）。建议由专门负责卡片设计的窗口重做提示词与卡片类型体系。"

这段话说明这个问题不是新发现——它在 R6 阶段就被用户指出过，也被记录在案，但一直没有安排专门的窗口去重做。

### 2.6 原始设计 vs 当前实现 对照表

| 维度 | 最初设计 | 当前代码 |
|---|---|---|
| 卡片类型体系 | 44 类型 / 8 分组 | 16 类型，无分组 |
| 情绪标签体系 | 46 标签 / 7 分组，带 `tag_id`/分组/自定义标记 | 自由文本 `label`，无枚举、无分组、无 ID |
| 卡片-情绪关联 | `related_emotion_tag_ids` 字段 | 不存在 |
| 卡片-观影记录关联 | `linked_viewing_ids` 字段 | 不存在 |
| "为什么重要"分析层 | `why_it_matters` 必需字段，承载分析结论 | 有生成、有校验，但界面从不展示/编辑 |
| 合并/拆分判断指令 | 明确规则 + CASE_001 具体示例 | 提示词只有"不要过度合并"一句，无合并指令、无示例 |
| 卡片数量 | 明确产品规则："不能预设上限" | Schema 硬编码 `maxItems: 7` |
| 重新生成机制 | 未明确规定，但应符合"整理"原则 | 不带上下文重复调用，无法避免近义卡片 |
| 无 AI 本地兜底 | 未直接规定 | 纯按标点分句取前三句，零分析 |
| 项目自身认知 | — | R6 文档已明确承认差距，标注"本轮未处理" |

### 2.7 复盘结论（供下一阶段参考）

把这几点放在一起看，问题不是"AI 能力不够"，而是**当初设计好的分析层被逐步简化掉了**：分类体系从 44/46 精简到 16/自由文本、关联字段被砍掉、合并/拆分这个最核心的判断指令没有被写进提示词、也没有验证案例真正测过这个能力、"为什么重要"这层结论生成了却没地方显示。这几件事叠加起来，AI 现在做的事情本质上退化成了"分句摘录"，跟当初 CASE_001 案例展示的"理解因果、判断颗粒度"的目标差距很大。

如果接下来要重做这个核心功能，从这份复盘看，有价值的起点包括：把 CASE_001/CASE_002 那种带着合并/拆分理由的验证案例重新当作提示词设计的基准，把 `why_it_matters` 接回界面，评估是否要恢复关联字段（至少 `related_emotion_tag_ids`），以及重新考虑"卡片数量不设上限、靠合并控制数量"这条被砍掉的产品规则是否要恢复。这些方向具体怎么取舍，建议开一个专门的设计复盘窗口来定。
